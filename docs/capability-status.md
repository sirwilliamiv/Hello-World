## The unit of work has changed

Phase 1 built the machine. Everything from here is filling the catalog, and a
capability is a well-defined unit of work: a specification, an npm package,
migrations, generated templates, smoke tests, contract tests against every
declared pair, a buyer-facing trigger sentence, a price, and an integration
weight. The brief is explicit that there is no informal path.

Two things now make this parallelisable in a way it was not before:

- **Specifications are the coordination mechanism.** A capability's `exposes`
  block is a contract another capability can be written against before its
  implementation exists. That is how six agents built sixteen packages
  concurrently without blocking on each other.
- **`forge lint` enforces the boundary mechanically.** An undeclared
  cross-capability import fails CI rather than review.

The constraint is no longer coordination. It is that each capability needs its
declared relationships to be *correct*, because the plan output, contract tests,
integration pricing, and client documentation are all derived from them.

## What to build first, and why

Wave 1 is 22 capabilities. Building it breadth-first would take a long time and
sell nothing. Three subsets are worth more than their size, for different reasons.

### 1. The four that change every other capability

These are structural. Building a capability before them means rewriting it after.

| Capability | Why it must come early |
|---|---|
| **`org.teams`** ($7,500, weight 6) | Adds an organization reference to **every** tenant-scoped entity. The catalog says so plainly: *"Adding this after launch is expensive; deciding it at manifest time is free."* Every capability written before it needs its queries revisited. Highest weight in the catalog. |
| **`audit.history`** ($4,500) | A hard dependency of `ai.agents` and `support.impersonation`, and it upgrades `kernel.audit`. Subscribes to everything, so it is cheap to add and gets more valuable with every capability that follows. |
| **`access.rebac`** ($9,500) | Upgrades `kernel.access`. Every capability declaring protected resources must publish a relation schema — retrofitting that across 40 capabilities is far worse than 5. |
| **`ai.gateway`** ($7,500) | Every AI capability routes through it; a direct provider call from anywhere else is a CI failure. Gates `docs.extraction`, `ai.retrieval`, `ai.agents`, `ai.evals` — $53,000 of wave 2 and 3. |

**These three are also the upgrade capabilities that need the runtime
substitution treatment** described in ARCHITECTURE.md §3: `access.rebac` over
`kernel.access`, `audit.history` over `kernel.audit`, and `comms.email` over
`kernel.mail`. `ops.queue` already demonstrates the pattern — the superseded
package forwards to an installable backend so package-to-package calls are
substituted too, not just the generated wiring.

### 2. The shortest path to a sellable package

The catalog's Part Three names the compositions that make a product feel like
one system. Two are reachable soonest:

**Quote → sign → deposit** — `docs.signature` + `pay.deposits` on what exists.
Needs `comms.email` (wave 1) then `docs.signature` (wave 2). Four capabilities,
about $19,500, and it closes a complete commercial loop.

**Stop Typing Invoices** — `docs.extraction` + `integrate.accounting` +
`ai.agents`. The catalog calls this the highest-value composition. It needs
`ai.gateway`, `integrate.connections`, `audit.history` and `automation.rules`
first: seven capabilities, ~$66,000, spanning all three waves.

### 3. The one that reduces future custom work

**`ops.formbuilder`** ($13,500) has no dependencies and is in wave 1. The catalog
says it *"absorbs the long tail of client requests that would otherwise become
custom work, and it should be recommended aggressively for that reason."* Client-
defined forms create real entities, so submissions inherit permissions, audit,
search and reporting automatically. It is the capability that most reduces the
pressure to write bespoke code — which is the pressure that fragments a fleet.

### Suggested order

1. `org.teams`, `audit.history`, `access.rebac`, `ai.gateway` — structural, parallel
2. `comms.email`, `integrate.connections`, `ops.formbuilder`, `pay.ledger` — unblocks the most downstream work
3. `docs.signature` + `pay.deposits` — first complete commercial loop
4. `automation.rules`, then `docs.extraction` + `integrate.accounting` + `ai.agents`

## Open work on what is already built

Filling the catalog is not the only thing outstanding. These affect every
capability that follows, so they are worth clearing first.

| Item | Why it matters |
|---|---|
| **The secrets provider resolves nothing** | The manifest binds credentials by `secret_ref` and `forge validate` enforces the binding, but `internal/provider/` contains `codegen` only. Values come from the environment. Every capability with credentials inherits this. |
| **22 of 31 slots are unaudited** | Three slots in `kernel.ui` were declared but dead — never called, unreachable, or their return value discarded. Nine capabilities have never been checked. A client writes logic into a dead slot and nothing happens, with no way to tell a wrong implementation from an unwired one. |
| **No catalog snapshot exists** | §8 says clients pin to a dated, immutable snapshot verified by the full contract test suite. `catalog/snapshots/` is empty; manifests name `2026-07-15`, which nothing produces or verifies. |
| **Contract tests are declared, not generated** | Specs declare `tests.contract` with `mandatory: true` and validation checks a test *exists*, but nothing generates or runs them against a synthetic product. §14.6 says these belong catalog-side. This gap widens with every declared pair. |
| **A real Stripe charge is unverified** | Needs credentials. See `docs/stripe.md`. |
| **`docs/catalog.md` is a placeholder** | The prose catalog is the specification this engine satisfies and is not in the repository. From Phase 2 it should be generated *from* the JSON so the two cannot diverge. |

## Two findings worth acting on before Phase 2

**Event names collide across capabilities.** `ops.queue` and `ops.dispatch` both
publish `job.started`, with unrelated payloads. A consumer cannot tell them
apart and contract versioning does not help, because the versions are
independent. `forge validate` catches it (FORGE013) but only once both are in
one product. The fix is namespacing (`queue.job.started` / `dispatch.job.started`)
and it is cheaper now, before `ops.dispatch` exists, than after.

**`integrate.custom` is the escape hatch and needs a policy.** It is the
sanctioned way to build something outside the catalog, priced per engagement. The
catalog says three clients needing the same connection is the trigger to promote
it to a first-class capability. Nothing tracks that today. Without a mechanism,
custom work accumulates invisibly — which is the failure this system exists to
prevent.

## Definition of done for a capability

Derived from `schemas/capability.schema.json` and the brief. A capability is not
finished until all of these hold:

- [ ] Specification validates against the capability schema
- [ ] Every relationship declared: `requires`, `enhances`, `conflicts`, `upgrades`, `owns`, `extends`, `publishes`, `consumes`, `exposes`, `registers`, `external`
- [ ] Buyer-facing `trigger` sentence, `price`, and `integration_weight`
- [ ] npm package implementing every name in `exposes`
- [ ] Every slot context exposes `proceed()`, and every slot is invoked on a real path with its return value honoured
- [ ] Migrations with working rollbacks, applied against real Postgres
- [ ] Event payload schemas registered at import — the bus refuses unregistered schemas, and two capabilities shipped without this
- [ ] Smoke tests for every `tests.smoke` entry
- [ ] Contract tests for every declared pair, `mandatory: true` where the catalog says so
- [ ] `forge lint` clean — no undeclared imports
- [ ] Generated output within the 400-line budget, or `scope: "graph"` where it is graph-derived
- [ ] If it is an upgrade: satisfies the full exposed interface of what it replaces, ships a migration, and forwards through an installable backend so package-to-package calls substitute too
